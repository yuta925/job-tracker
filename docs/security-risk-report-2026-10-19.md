# Waypoint セキュリティリスク調査レポート

作成日：2026年10月19日

対象：`job-tracker` / 調査時コミット `403b4df`

対象範囲：前回の監査で優先度「高」とした、Next.jsの既知脆弱性とGoogle Calendar連携トークンの保管・アクセス設計

## 1. 結論と対応順序

優先する対策は、**Next.jsを含む依存パッケージの更新**と、**Google Calendarトークンの暗号化・サーバーへのアクセス集約**である。

| ID | 優先度 | どこで発生しうるか | 主な影響 | 推奨する対策 |
| --- | --- | --- | --- | --- |
| SEC-01 | 高・先に対応 | 公開されたNext.jsサーバーのApp Router、Server Functions、Proxyによる認証処理 | 特殊なHTTPリクエストによる処理停止、条件次第でProxyの認証判定の迂回 | 修正済みリリースへの依存更新、ページ・API・データ操作ごとの認証認可、実際のビルドで回帰確認 |
| SEC-02 | 高・続けて対応 | Google CalendarのOAuthコールバック、`google_calendar_tokens`テーブル、Supabase Data API | トークン漏えいによるCalendarイベントの不正閲覧・変更 | トークンの暗号化、クライアントからの直接アクセス禁止、認証済みサーバー経由の操作、既存データの移行 |

このレポートは対策設計の資料であり、脆弱性の修正、DBの変更、本番への攻撃リクエスト送信、トークンの取得・失効は実施していない。侵害が起きていることを示す調査結果でもない。

## 2. 調査方法と確度

- ソースコード、DBマイグレーション、依存定義・ロックファイル、CI設定を確認した。
- 前回の監査で取得した`npm audit --omit=dev --json`の結果と、今回の`npm ls next --depth=0`を照合した。インストール済み・ロック済みのNext.jsはともに`16.2.1`だった。
- 公式のNext.jsセキュリティ勧告、Google OAuth・Calendar API、Supabase Data APIの資料を確認した。
- 本番デプロイの実バージョン・ビルド条件、本番DBのテーブル権限とAPI公開スキーマ、実際の攻撃成立は未検証である。マイグレーションと本番DBが同一であることも、このレポートの作成時には実測していない。

以下では、「コードで確認済み」と「設定や追加の侵害条件に依存する想定」を区別する。

## 3. SEC-01：Next.jsの既知脆弱性

### 3.1 どこで発生しうるのか

ブラウザからアクセスされるNext.jsサーバー上で発生しうる。特に、App RouterのServer Functionsへのリクエスト処理と、保護対象ページに対するProxyの適用処理が対象になる。

| 根拠となるファイル | 確認した内容 |
| --- | --- |
| [web/package.json](../web/package.json) 19行目、[web/package-lock.json](../web/package-lock.json) | 定義は`next: ^16.2.1`、ロック・インストール済みは`16.2.1` |
| [web/proxy.ts](../web/proxy.ts) 4・8行目 | リクエストを`updateSession()`へ渡し、matcherで適用対象を決定 |
| [web/lib/supabase/middleware.ts](../web/lib/supabase/middleware.ts) 28・47行目 | `getUser()`でログインを確認し、未ログインならリダイレクト |
| [web/lib/google_calendar/actions.ts](../web/lib/google_calendar/actions.ts) 1・65行目 | App RouterのServer Actionsを使用 |
| [web/app/dashboard/page.tsx](../web/app/dashboard/page.tsx) 6行目、[web/app/profile/page.tsx](../web/app/profile/page.tsx) 7行目 | ページ内でも認証を再確認している |

監査結果は、対象パッケージの集計として**9件：Critical 1件、High 6件、Moderate 2件**だった。これはCVEの件数や、アプリ上で悪用を確認した件数ではない。Next.jsには複数の勧告が紐づいており、使用機能や環境により影響が異なる。

### 3.2 想定される発生経路と影響

**A. Server Functionsの処理を通じたサービス停止**

```text
外部から特殊なHTTPリクエスト
  → Next.jsがServer Function向けデータを解析
  → 過大なCPU消費
  → 画面表示や保存処理の遅延・失敗、サービスの利用不能
```

公式勧告では、App RouterのServer Functionエンドポイントへの細工したリクエストが、デシリアライズ時にCPUを過剰消費させる可能性がある。`16.2.1`は対象範囲であり、アプリもServer Actionsを使っているため、更新を急ぐ理由になる。関数本体でのログイン確認だけで、解析段階の負荷を防げるとは限らない。[Next.jsのDoS勧告](https://github.com/vercel/next.js/security/advisories/GHSA-q4gf-8mx6-v5v3)

**B. Proxyに期待した認証判定の迂回**

```text
外部から通常のページURLとは異なるApp Router用リクエスト
  → 本来適用すべきProxyの判定が適用されない場合がある
  → Proxyだけで保護していたコンテンツへ到達するおそれ
```

公式勧告には、segment-prefetchなどの経路でmiddleware／Proxyの認可判定を迂回する問題がある。元の修正は`16.2.5`、Turbopackと`middleware.ts`に関する追加修正は`16.2.6`である。本アプリは`proxy.ts`を使用しており、追加修正固有の条件と元の問題を同一視せず、実際のビルドで影響を確認する必要がある。[元の勧告](https://github.com/vercel/next.js/security/advisories/GHSA-267c-6grr-h53f)、[追加修正の勧告](https://github.com/vercel/next.js/security/advisories/GHSA-26hh-7cqf-hhc6)

**このアプリに既にある防御：** ホームとプロフィールはページ内でも`getUser()`を実行し、未ログインならリダイレクトする。CalendarのServer Actionsにも認証と`user_id`の確認がある。DBにはユーザーごとのRLSもある。このため、Proxyを迂回できることだけから、他人の応募情報や自己分析データが読めるとは断定できない。

**Critical表示の扱い：** 監査には、OSや画像処理機能などの条件に依存するリモートコード実行の勧告も含まれる。例えば`next/og`の`ImageResponse`の問題は、攻撃者が制御する値をNode.jsのSVG画像生成に渡す条件がある。今回、アプリコードに`next/og`／`ImageResponse`の利用は見つからなかった。したがって「Criticalの報告がある＝現在このアプリでコード実行が成立する」とは評価していない。ほかの勧告についても本番の実行経路の確認が必要である。[ImageResponseの公式勧告](https://github.com/vercel/next.js/security/advisories/GHSA-vcvr-r3jv-pc5j)

### 3.3 どう対策するか

1. **Next.jsと関連依存を修正済みバージョンへ更新する。** `package.json`だけでなく`package-lock.json`を更新し、クリーンインストールで再現できるようにする。上記の個別勧告の修正バージョンは、その問題だけの修正を示す。`16.2.6`への更新だけで全件解消とせず、対応時点で公開済みの勧告を再確認する。
2. **Proxyに加えて、処理ごとに認証・認可する。** 現在のホーム・プロフィールのページ内チェックを維持する。すべての保護対象API・Server Actionで本人を確認し、対象データの所有者を照合する。クライアントから渡された`user_id`を、そのまま本人として扱わない。
3. **DBのRLSを維持する。** Next.js側の不具合があっても、未認証者や別ユーザーのデータ操作が拒否される構成を保つ。
4. **更新までの間は公開経路の負荷制御を確認する。** ホスティング側のWAFやレート制限を補助として使う。これはフレームワーク更新の代替にはしない。開発サーバーも外部へ無制限に公開しない。
5. **依存監査を継続する。** [現在のCI](../.github/workflows/ci.yml)はlint・型・テスト・ビルドを実行するが、明示的な依存脆弱性監査のステップはない。監査や更新通知を追加し、High以上の指摘をレビュー対象にする。

### 3.4 対策完了の確認方法

- 更新後に`npm ci`と`npm ls next --depth=0`で、実際に修正済みバージョンが入ることを確認する。
- `npm audit --omit=dev`を再実行し、対象の勧告が解消したことを確認する。残る指摘は対象バージョン・使用経路・暫定措置を個別に記録する。
- lint、型チェック、テスト、本番ビルドを通す。ログイン、パスワード再設定、企業情報保存、Gmail・Calendar連携の正常動作を確認する。
- ステージングの本番相当ビルドで、通常URLとApp Routerのデータ取得経路の双方について、未ログイン時に保護データが返らないことを確認する。別ユーザーのレコードへのアクセスも拒否されることを確認する。
- 本番に同じ更新が反映されたことをデプロイ記録で確認する。負荷を発生させる再現試験は、本番では実施しない。

## 4. SEC-02：Google Calendarトークンの平文保管とアクセス範囲

### 4.1 どこで発生しうるのか

Google連携完了時の保存、DB・バックアップへのアクセス、Supabase Data API経由の読み取りに関係する。

| 根拠となるファイル | 確認した内容 |
| --- | --- |
| [web/app/api/google-calendar/callback/route.ts](../web/app/api/google-calendar/callback/route.ts) 25・32行目 | Googleから受け取ったトークンを保存関数に渡す |
| [web/lib/google_calendar/queries.ts](../web/lib/google_calendar/queries.ts) 26行目 | アクセストークンと更新トークンを暗号化せず保存 |
| [web/supabase/migrations/0013_add_google_calendar_tokens.sql](../web/supabase/migrations/0013_add_google_calendar_tokens.sql) 4・14行目 | トークンをTEXT列に保存し、本人の行のSELECT・変更を許可 |
| [web/lib/supabase/server.ts](../web/lib/supabase/server.ts) 7行目 | サーバーのDB操作も、公開キーと利用者セッションで行う |
| [web/lib/google_calendar/client.ts](../web/lib/google_calendar/client.ts) 28行目 | 保存した更新トークンとOAuthクライアント設定でアクセストークンを更新 |
| [web/app/api/google-calendar/auth/route.ts](../web/app/api/google-calendar/auth/route.ts) 22行目 | `calendar.events`スコープを要求 |
| [web/lib/google_calendar/connection.ts](../web/lib/google_calendar/connection.ts) 15行目 | 連携解除はDB行の削除のみで、Google側のトークン失効処理は見つからない |

「平文」とは、**アプリがDB列へ保存する前に暗号化していない**という意味である。Supabaseのストレージ全体の暗号化やTLSが無効だと確認したわけではない。ストレージ暗号化があっても、正規のSELECTやDBエクスポートでは列の値を読めるため、対策の対象は異なる。

### 4.2 想定される発生経路と成立条件

**A. 利用者セッションを足掛かりにしたトークン取得**

```text
XSSやセッション窃取など、別の侵害が成立
  → 被害者としてSupabase Data APIへアクセス
  → 本人のトークン行を読むRLS条件を満たす
  → 平文のGoogleトークンが漏れるおそれ
```

この経路には、当該テーブルがData APIの公開対象であり、`authenticated`ロールにテーブル／列のSELECT権限があることも必要になる。マイグレーションには本人の行を読むRLSポリシーがあるが、**本番の公開スキーマ・GRANT設定と実際のREST応答は未検証**である。Supabaseではテーブル権限とRLSを組み合わせてアクセスを制御するため、この確認が必要である。[Supabase Data APIの保護](https://supabase.com/docs/guides/api/securing-your-api)

現状のプロフィール画面はクライアントへ連携状態の真偽値だけを渡しており、画面から生のトークンを配信する実装は確認していない。また、RLSは他人の行の読み取りを制限している。問題は、本人のセッションが侵害された際に、生のGoogle認証情報まで取得可能になる設計である。XSSそのものや他ユーザーへの越権アクセスが見つかったという指摘ではない。

**B. DB・バックアップ・管理権限からの漏えい**

DBの読み取り権限、SQLダンプ、バックアップのエクスポート、管理アカウントが侵害された場合、平文トークンが露出しうる。アプリのログインセッションが終了しても、Googleトークンの有効性とは別なので、アプリからログアウトするだけでは漏れたGoogleトークンは無効にならない。

### 4.3 何が起こるか

`calendar.events`は、カレンダーのイベントを閲覧・編集する権限である。アプリ自身は主に`primary`カレンダーへの予定追加に使っているが、漏れたトークンの権限はその画面操作や就活予定だけに限定されない。Google上で許可されている範囲のイベント情報や操作が影響対象になる。[Google Calendarのスコープ一覧](https://developers.google.com/workspace/calendar/api/auth)

- **アクセストークン漏えい：** 有効期間中、そのトークンのスコープ内でAPIを不正利用されるおそれがある。
- **更新トークン漏えい：** アクセスを更新するための長期的な認証情報が露出する。Webサーバー用OAuthクライアントの更新処理では通常`client_id`・`client_secret`も使うため、「更新トークン単体さえあれば無条件に永久利用できる」とは断定しない。クライアント秘密情報の漏えいやサーバー侵害が重なると、継続アクセスのリスクが高まる。[Google Webサーバー向けOAuth仕様](https://developers.google.com/identity/protocols/oauth2/web-server#offline)
- **連携解除後：** 現在のDB行削除だけでは、既に外部へ漏れたトークンのGoogle側での失効を保証できない。

### 4.4 どう対策するか

**① トークンをサーバーだけが扱う構成にする。**

クライアントには「連携済みか」と操作結果だけを返す。トークンテーブルはData API非公開のスキーマへ移すか、ブラウザ用の`anon`／`authenticated`ロールから直接SELECT・INSERT・UPDATE・DELETEできないようにする。必要なDB操作は認証済みのサーバー処理に集約する。[Supabase Data APIの保護](https://supabase.com/docs/guides/api/securing-your-api)

ただし、現在のサーバー処理も利用者セッションでDBへ接続しているため、**権限だけを取り消すと連携・更新・解除も停止する**。サーバー専用のアクセス経路を先に設計する。専用DBロールなどで最小権限にし、もしRLSを迂回する管理キーを使う場合は、呼び出しごとに`getUser()`で本人を確定し、対象の`user_id`をサーバーで固定する。管理キーはブラウザや`NEXT_PUBLIC_`変数へ渡さない。

**② アクセストークンと更新トークンを暗号化する。**

AES-256-GCMなどの認証付き暗号を使い、ランダムなIVと認証タグを保存する。鍵はDB・リポジトリから分離してサーバーの秘密情報として管理し、鍵の世代を識別できる形式にする。既存の[Gmail暗号化処理](../web/lib/gmail/token-crypto.ts)を参考にできるが、Calendar用の鍵を分けると影響範囲とローテーションを管理しやすい。暗号化だけでサーバー自体の侵害を防げるわけではなく、アクセス制限と併用する。Googleもサーバーに保存する利用者トークンの暗号化を推奨している。[Google OAuthのベストプラクティス](https://developers.google.com/identity/protocols/oauth2/resources/best-practices)

**③ 保存・取得・更新・解除をまとめて切り替える。**

OAuthコールバック、期限切れ時の更新処理、予定追加、連携状態取得、連携解除を対象にする。トークン操作モジュールを`server-only`にし、クライアントから誤ってインポートできないようにする。トークンは画面のprops・APIレスポンス・ログ・例外本文に含めない。

**④ 既存トークンを移行し、平文列を残さない。**

新しい暗号化形式を読み書きする処理を用意し、管理された移行処理で既存データを暗号化する。動作と件数を確認した後、平文列を除去する。移行用ファイルや過去のバックアップにも平文が残る可能性があるため、アクセス権限・保管期間・復元時の再移行手順も確認する。サービス停止が許容できるなら、メンテナンス中に移行とデプロイをまとめて行う方法もある。

**⑤ 漏えい時と連携解除時の失効手順を設ける。**

通常の連携解除では、Google側の認可／トークン失効とローカル削除を組み合わせ、失効に失敗した場合の再試行・案内を設計する。侵害の疑いがある場合は対象のGoogle認可を取り消し、必要な秘密情報をローテーションしたうえで再連携する。暗号化への移行だけでは既に漏れたトークンは失効しない。[Google OAuthのベストプラクティス](https://developers.google.com/identity/protocols/oauth2/resources/best-practices)

**⑥ 要求する権限を必要最小限にする。**

主カレンダーへの追加を続ける場合は`calendar.events.owned`などへの縮小を検討する。アプリ専用カレンダーへ変更できるなら`calendar.app.created`も候補になる。いずれも機能・操作性への影響を確認して決める。単に書き込み権限を削ると、現在の予定追加機能が動かなくなる。[Google Calendarのスコープ一覧](https://developers.google.com/workspace/calendar/api/auth)

### 4.5 対策完了の確認方法

| 確認対象 | 合格条件 |
| --- | --- |
| 未ログイン・ログイン済みのブラウザからのDBアクセス | どちらからもトークンの生値・暗号文を直接取得／変更できない |
| サーバーの本人確認・所有者確認 | 利用者Aが利用者Bの連携情報を取得・更新・削除できない。クライアント指定の`user_id`で所有者を変更できない |
| DB内のデータ | 保存値は暗号文であり、既存行も移行済み。平文列が残っていない |
| 暗号化処理 | 復号・改ざん検知・鍵の不備をテストし、復号失敗時に平文として扱うフォールバックがない |
| 正常動作 | 連携、連携状態表示、予定追加、アクセストークン更新、連携解除が動く |
| ブラウザ・ログ | レスポンス、クライアントバンドル、ログ、例外にトークンや秘密鍵が含まれない |
| Google側の失効 | 連携解除・漏えい対応後、対象の認可が失効している。認可失効がGmail連携にも影響する構成なら、その影響も確認する |

実トークンをテスト結果・スクリーンショット・コミットへ残さない。権限の拒否確認はテスト専用ユーザーで行う。

## 5. 実施順序と完了判定

1. **依存更新を先行する。** Next.js・関連パッケージ・ロックファイルを更新し、監査と既存機能の回帰確認を行う。本番の実行バージョンも確認する。
2. **Calendarの本番設定を読み取り専用で確認する。** テーブルのAPI公開状況、ロール／列の権限、実際のRLSを確認し、SEC-02のData API経路が成立するか確定する。報告には権限と結果だけを残し、トークン値は取得・保存しない。
3. **Calendarのアクセス経路・暗号化・移行を一体で実装する。** 新しいサーバー経路の準備、既存行の移行、直接アクセス権限の撤去、正常動作確認を整合させる。旧実装へ戻すだけのロールバックでは平文保管が復活するため、安全な復旧・再連携手順も用意する。
4. **失効と運用手順を整える。** 連携解除、鍵の更新、再連携、移行済みバックアップの復元手順を記録する。

SEC-01は「修正済み依存が本番で動き、対象勧告が解消し、認証境界の回帰確認が通ること」、SEC-02は「クライアントがトークンに直接アクセスできず、保存値が暗号化され、本人以外の操作が拒否され、正常な連携・失効が動くこと」を完了条件とする。

前回の監査にあった漏えいパスワード保護の無効化とDB関数の`search_path`警告は、今回の高優先度2件とは別の後続対応として残る。本番HTTPヘッダーや侵害履歴の調査も、このレポートの対象外である。
